# eve-trader v1 spec: Rens station-trading opportunity finder

Status: **implementation-ready**. Compiled from the decision tickets resolved on the
[wayfinder map (#1)](https://github.com/mgoodness/eve-trader/issues/1); each section
cites the ticket(s) it derives from. This document is the destination of that map —
no further planning ticket is expected before implementation begins.

## 1. Overview

A single-user, hosted web tool that scans Rens's own order book for profitable
station-trading opportunities, ranks them by expected daily profit, and presents
them in a sortable table. Auth is a one-time EVE SSO login used only to retrieve
the trading character's skills (Broker Relations, Accounting) so fee/tax math is
accurate for that specific character.

**Explicitly out of scope for v1** (see map's Out of scope section):
- Regional arbitrage (Jita/Amarr/Dodixie/Hek ↔ Rens) — Rens station trading only.
- Transaction tracking / buy-sell order & inventory management — a possible v2.

## 2. Architecture

- **Language/runtime:** Go, single static binary.
- **Persistence:** embedded SQLite (see §5 for schema).
- **Frontend:** Go `html/template` + htmx, server-rendered, no SPA/build step.
- **Hosting:** one GCP Always Free `e2-micro` VM, Docker-deployed. *(#4)*
- **Auth:** EVE SSO (ESI) OAuth2 + PKCE, one-time login. *(#6)*
- **External data:** ESI only — no third-party market data source. *(#2)*

## 3. Data source (ESI)

*(Decided in [Research: ESI market data source for Rens (#2)](https://github.com/mgoodness/eve-trader/issues/2))*

- **Order book:** `GET /markets/{region_id}/orders/` with `region_id=10000030`
  (Heimatar), paginated (~73 pages, ~15–20 MB per full pull), filtered
  client-side to Rens's `location_id=60004588`. ESI has no station-scoped order
  endpoint for NPC stations — pulling the region and filtering locally is the
  standard, and only, pattern.
- **Liquidity/volume:** `GET /markets/{region_id}/history/` per `type_id`
  returns daily `volume`/`order_count`. This is region-scoped, not
  station-scoped — accepted as a v1 approximation since Rens dominates
  Heimatar's trade (documented prominently in the UI, see §6).
- **Poll cadence:**
  - Order book: no more often than every ~300s (ESI's own `Expires` cache
    header).
  - History: once/day, aligned to ESI's cache reset at 11:05 UTC.
- **Rate limits:** not a real constraint at this scale (~876 req/day for the
  order-book poll vs. a 12,000/15-min ceiling).
- **No third-party source needed.** Fuzzwork Market Data was evaluated and
  rejected for v1 (its aggregates endpoint can't replace raw order rows) —
  worth revisiting only if scope grows beyond Rens-only.

## 4. Profitability & ranking formula

*(Decided in [Research #3](https://github.com/mgoodness/eve-trader/issues/3) and
[Adapt profit formula & ranking algorithm for eve-trader v1 (#5)](https://github.com/mgoodness/eve-trader/issues/5))*

```
π   = P_s − P_b − (P_b×R_b) − (P_s×R_b) − (P_s×R_t)     // profit per unit
R_b = 3% − 0.3%×BrokerRelations                          // broker fee rate
R_t = 7.5%×(1 − 0.11×Accounting)                          // sales tax rate
M   = (P_s − P_b) / P_s × 100%                            // gross margin %
V_d = average(volume) over the retained market_history window  // avg daily volume
EDP = π × V_d                                             // expected daily profit — PRIMARY RANK
```

- **Ranking:** primary sort is **EDP (ISK/day) descending**. Margin % and
  ISK/unit are shown as visible columns, not folded into the sort, so the
  trader can judge liquidity risk vs. margin at a glance.
- **Skill inputs:** `BrokerRelations` and `Accounting` are the character's
  `active_skill_level` (not `trained_skill_level`) for skill IDs `3446` and
  `16622` respectively, read via ESI (see §5 `character_skill` table). Missing
  skill ID = level 0.
- **Standings term deliberately omitted for v1.** CCP's real broker-fee
  mechanic also includes `−0.03%×FactionStanding − 0.02%×CorpStanding`; v1
  skips it to avoid the extra `esi-characters.read_standings.v1` scope and
  NPC-corp/faction matching. This makes v1's numbers a conservative
  (slightly pessimistic) lower bound for characters with non-negative
  standings. See §8 for v1.1 follow-up.
- **Minimum broker fee floor:** `max(100 ISK, order_value × R_b)`, applied
  **per order** (and per relist), not per-unit — this only matters when
  sizing an actual order, not in the per-unit ranking math. No floor applies
  to sales tax, and the two fees don't interact.
- **v1 filter thresholds (hardcoded constants):**
  - Minimum margin: **5%**
  - Minimum daily volume: **10 units/day**
  - Not user-configurable in v1 (see §8).

## 5. SQLite schema

*(Decided in [Design v1 SQLite schema (#7)](https://github.com/mgoodness/eve-trader/issues/7))*

Five tables. `market_order` and `character_skill`/`esi_token` are current-state
caches; only `market_history` retains a rolling window. No order-level or
price history is kept anywhere — nothing downstream consumes it.

```sql
-- Current Rens order book. Upserted + hard-pruned every poll (~5 min).
CREATE TABLE market_order (
  order_id       INTEGER PRIMARY KEY,
  type_id        INTEGER NOT NULL REFERENCES item_type(type_id),
  is_buy_order   INTEGER NOT NULL,   -- 0/1
  price          REAL    NOT NULL,
  volume_remain  INTEGER NOT NULL,
  volume_total   INTEGER NOT NULL,
  min_volume     INTEGER NOT NULL,
  issued         TEXT    NOT NULL,   -- ISO8601
  duration       INTEGER NOT NULL,
  updated_at     TEXT    NOT NULL    -- timestamp of the poll that last saw this row
);
CREATE INDEX idx_market_order_type_id ON market_order(type_id);

-- 14-day rolling window of Heimatar-region daily volume, refreshed once/day.
-- V_d in the ranking formula is the average `volume` over this window,
-- computed at query time (not pre-aggregated).
CREATE TABLE market_history (
  type_id      INTEGER NOT NULL REFERENCES item_type(type_id),
  date         TEXT    NOT NULL,  -- ISO8601 date
  volume       INTEGER NOT NULL,
  order_count  INTEGER NOT NULL,
  PRIMARY KEY (type_id, date)
);

-- Lazy display-name cache. Populated the first time a type_id is seen in a
-- Rens pull; refreshed on a long cadence (e.g. weekly). Also stands in for
-- the "Rens-tradable" item set — no separate curated catalog.
CREATE TABLE item_type (
  type_id     INTEGER PRIMARY KEY,
  name        TEXT    NOT NULL,
  updated_at  TEXT    NOT NULL
);

-- Single row: the one trading character's fee/tax skill levels.
CREATE TABLE character_skill (
  character_id             INTEGER PRIMARY KEY,
  broker_relations_level   INTEGER NOT NULL,
  accounting_level         INTEGER NOT NULL,
  updated_at               TEXT    NOT NULL
);

-- Single row: OAuth refresh token (see §6).
CREATE TABLE esi_token (
  character_id              INTEGER PRIMARY KEY,
  owner_hash                TEXT    NOT NULL,
  encrypted_refresh_token   BLOB    NOT NULL,
  updated_at                TEXT    NOT NULL
);
```

**Refresh cadences** (independent, no cross-table write transaction needed):

| Table              | Cadence                                   |
|---------------------|--------------------------------------------|
| `market_order`      | ~every 5 min (ESI order-book cache window) |
| `market_history`    | daily, aligned to ESI's 11:05 UTC reset    |
| `item_type`         | weekly (names rarely change)               |
| `character_skill`   | daily                                      |
| `esi_token`         | on every SSO refresh-token rotation        |

## 6. OAuth / ESI auth flow

*(Decided in [ESI OAuth scope list & auth flow spec (#6)](https://github.com/mgoodness/eve-trader/issues/6))*

- **Scope:** `esi-skills.read_skills.v1` only. Market data and character info
  are public ESI endpoints — no token required for those. No wallet/assets/
  standings scopes requested in v1.
- **Endpoints:** authorization `https://login.eveonline.com/v2/oauth/authorize`,
  token `https://login.eveonline.com/v2/oauth/token`. PKCE (S256) is used —
  effectively mandatory under SSO v2.
- **Login trigger:** `/auth/login` is an unauthenticated route, visited
  manually and once by the tool's owner after deploy. No app-level password
  wall — a stranger hitting the route is just redirected into *your* EVE
  character's SSO login, which is useless to them. **This exposure is
  accepted, not mitigated**, appropriate for a single-user personal tool.
- **PKCE state/code_verifier:** held in a short-lived (few-minute), HMAC-signed
  cookie across the redirect round-trip — not server-side session state.
  Survives an app restart mid-flow.
- **Redirect URIs registered on the EVE developer app:**
  - Production: `https://<domain>/auth/callback` (domain is an operator-chosen,
    deploy-time value — see §7).
  - Local dev: `http://localhost:<port>/auth/callback`.
- **Token storage:** `esi_token` table (§5). Only the refresh token is
  persisted, AES-GCM-encrypted at rest (SQLite file could land in backups).
  The encryption key is injected via an environment variable (Docker
  Compose / systemd env file) — never committed to the repo or baked into
  the image. GCP Secret Manager is skipped as disproportionate for a
  single-user tool.
- **Access tokens:** minted fresh in-memory from the refresh token via
  `golang.org/x/oauth2`'s `TokenSource` before each ESI poll; never written to
  disk. Access tokens are short-lived JWTs (~20 min typical; read
  `expires_in` at runtime, don't hardcode).
- **Refresh-failure / re-auth UX:** refresh tokens rotate on every use and can
  be revoked at any time. When a refresh attempt fails, the app detects "no
  valid token," logs the failure, **stops polling ESI**, and the frontend
  replaces the opportunity table with a "Re-authenticate with EVE" banner
  (see §7) — no silent retry loop.
- **Owner-hash check:** the `owner` hash is stored (forward-compat/debugging
  value) but no mismatch-detection logic is built for v1 — acceptable risk
  for a personal tool authorizing your own character.

## 7. Frontend

*(Decided in [Prototype the opportunity-list frontend (#8)](https://github.com/mgoodness/eve-trader/issues/8);
prototype preserved on the
[`prototype/opportunity-list-frontend` branch](https://github.com/mgoodness/eve-trader/tree/prototype/opportunity-list-frontend/cmd/prototype-frontend))*

- **Layout:** one page, one dense table — every opportunity that passed the
  §4 filter thresholds, one row per item: **Item, Buy, Sell, Margin, ISK/unit,
  Vol/day, ISK/day**. No hero card, no per-item drill-down page — a
  single-user analytical tool favors seeing the whole ranked list at once.
- **Sorting:** every numeric column header is clickable (htmx `hx-get`
  swapping the table body); default sort is **ISK/day descending**. No
  pagination — the post-filter row count is expected to be dozens, not
  thousands.
- **Footnote:** a persistent header footnote states the Heimatar-region-volume
  caveat from §4/§3 — it qualifies every row's Vol/day and ISK/day figures.
- **Auth entry point:** no separate login page. When unauthenticated or on
  refresh failure, the table area is replaced wholesale by a centered
  "Re-authenticate with EVE" banner/button hitting `/auth/login` (§6).

## 8. Deployment (GCP e2-micro)

*(Decided in [Research: GCP free-tier e2-micro fit (#4)](https://github.com/mgoodness/eve-trader/issues/4),
domain/TLS and ops details synthesized here per this ticket's scope)*

- **Instance:** one Always Free `e2-micro`, in **one of** `us-west1`,
  `us-central1`, or `us-east1` (hard Always-Free region constraint — pick one
  explicitly).
- **Disk:** `pd-standard`, ≤30 GB, to stay within the free allowance.
- **Container:** slim/distroless Go image, SQLite embedded in-process, no
  sidecars. Add a 1–2 GB swap file as an OOM safety net (1 GB RAM is real but
  tight for this shape). Bare-binary + systemd is a documented fallback if
  memory pressure appears in practice.
- **Firewall:** explicit inbound rule for HTTPS (443) only; default-deny
  everything else.
- **Egress:** a non-issue — inbound ESI pulls (the ~15–20 MB Rens/Heimatar
  data) don't count against the 1 GB/month free egress allowance; only the
  tiny outbound request + the owner's own browser traffic count, realistically
  tens of MB/month.
- **Recurring cost:** the external IPv4 address (~$3.65/month) is the one
  real cost not covered by Always Free.
- **TLS / domain:** EVE SSO's callback requires HTTPS, which a bare VM
  doesn't provide. Run **Caddy** in front of the Go binary — Caddy's
  automatic HTTPS (Let's Encrypt) needs only a `Caddyfile` pointing at a
  domain name and the local app port:
  ```
  <domain> {
    reverse_proxy localhost:8080
  }
  ```
  The domain name itself is an operator-provided, deploy-time value (buy any
  domain and point an A record at the VM's external IP) — not a modeling
  decision this spec can fix in advance. Register both the production
  (`https://<domain>/auth/callback`) and local-dev (`http://localhost:<port>/auth/callback`)
  redirect URIs on the EVE developer app per §6.
- **Logging:** the app logs structured lines to stdout; Docker's default
  `json-file` log driver captures them, viewable via `docker logs`. No
  external log aggregation service for v1 — single-user, low volume doesn't
  justify one.
- **Monitoring:** none beyond the app's own signals — the re-auth banner (§6,
  §7) is the primary "something's wrong" indicator, and `docker logs` covers
  the rest. No external uptime-monitoring service is provisioned for v1;
  optionally wire a free third-party checker (e.g. UptimeRobot) later if
  desired, but it's not part of this spec.
- **Deployment pipeline:** a post-Wayfinder refinement, tracked in the
  product issue and its deployment child ticket, delivers the application
  artifact only; Terraform infrastructure provisioning remains separate.
  Successful `main` CI runs publish immutable candidate images to a container
  registry, and production deployment requires approval through a protected
  GitHub Actions environment with required reviewers. Deployments use a
  dedicated SSH key, are serialized, and target an already-bootstrapped VM.
- **Deployment verification:** the VM pulls the immutable image while keeping
  SQLite as runtime state mounted into the active container. Completion polls
  the publicly trusted HTTPS route through Caddy for both an unauthenticated
  `/healthz` endpoint and the public homepage within a bounded readiness window.
  Pull or startup failure leaves the known-good version active. The workflow
  records the image identity, approver, timestamp, target VM, and health result.
- **Secrets and rollback:** production secrets are provisioned separately by a
  controlled GitHub Actions operation, with restrictive permissions and never
  baked into the image or printed in logs. A fixed, documented set of recent
  images remains available for manual rollback. Normal rollback restores the
  prior image without replacing SQLite; database restoration is separate.
  Schema-changing releases require backward-compatible migrations and a
  pre-migration SQLite backup. Registry visibility/authentication is deployment
  configuration, not a product constraint, provided image contents contain no
  secrets.
- **Operator contract:** the repository documents VM bootstrap, registry and
  protected-environment setup, SSH credentials, VM address, production
  configuration, secret provisioning, deployment, health checks, and rollback.
  GitHub Actions status is sufficient v1 failure notification; no external
  alerting is required.
- **Backup:** a daily cron job on the VM copies the SQLite file
  (`sqlite3 eve-trader.db ".backup /backups/eve-trader-$(date +%F).db"`) into
  a local rotating set (e.g. last 7 daily copies, pruned on write). No
  off-VM/cloud backup destination for v1 — VM loss is an accepted risk for a
  single-user personal tool with no financial/irreplaceable data at stake
  beyond the refresh token (which is trivially re-obtained via `/auth/login`).

## 9. Future work (deferred past v1)

These are known, deliberately deferred refinements — not open questions
blocking this spec, and not part of the v1 build:

- **Broker-fee standings term** (§4): CCP's real mechanic includes a
  faction/corp standings adjustment that v1's formula omits. Would require
  the `esi-characters.read_standings.v1` scope and NPC-corp/faction ID
  matching. Revisit as a v1.1 refinement.
- **User-configurable filter thresholds** (§4): v1 hardcodes the 5% margin /
  10 units-per-day minimums as constants. Making them adjustable (config file,
  env vars, or a UI control) is deferred to a later version.
- **Regional arbitrage** and **v2 transaction/inventory tracking** — see the
  map's Out of scope section; these are separate future efforts, not v1.1
  refinements of this spec.
