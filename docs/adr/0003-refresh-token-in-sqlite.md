# Store the OAuth refresh token in SQLite, not the secrets env file

Every other secret (ESI OAuth Client ID/Secret, Discord webhook URL) lives in a restricted-permission env file on the VM, loaded into the container at startup. The OAuth refresh token is the one exception: it rotates on every use (ESI issues a new refresh token each time the old one is redeemed, per the research in issue #8), so the app needs to read *and* overwrite it at runtime — something a static, container-startup-time env file can't do without external tooling to rewrite the file and restart the container on every token refresh. We chose to store the refresh token in the app's own SQLite database (a single-row table) instead, since the app already owns that database and has read/write access to it during normal operation. This makes the refresh token's storage location inconsistent with every other secret's — a future reader should know this is deliberate, not an oversight.
