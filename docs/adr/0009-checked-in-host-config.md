# Check host config into the repo, with manual sync

Caddy's TLS/reverse-proxy config and how the app container + Watchtower are actually invoked used to live only on the production VM — nothing in the repo could be diffed against what was actually running, and rebuilding the host after loss meant re-deriving all of it from ADR-0004/ADR-0008 and memory.

`deploy/Caddyfile` now captures the real, current reverse-proxy config, pulled directly off the host. `scripts/provision-host.sh` is the checked-in capture of how the app container, Watchtower, and Caddy are actually run — the exact `docker run` invocations, images, ports, volumes, and env var *names*, not a separate declarative file. Real secret values go in `~/eve-trader.env` and `~/watchtower.env` on the host only (see `deploy/eve-trader.env.example` / `deploy/watchtower.env.example` for what each needs), never in the repo. Given a bare e2-micro VM with those two files already in place, `scripts/provision-host.sh` brings up the whole stack: ensure the `eve-trader-net` bridge network exists, copy over `deploy/Caddyfile`, and (re)start all three containers.

**Why a script of `docker run` commands instead of `docker-compose.yml`:** the production VM runs Google's Container-Optimized OS (COS) — its root filesystem is read-only and `/home` is mounted `noexec` (confirmed live while writing this script: a compose binary dropped into `$HOME` couldn't even execute). COS has no package manager, so a conventional `apt`/`get.docker.com`-style "install compose" step doesn't apply, and there's nowhere writable-and-executable to put a standalone compose binary. Docker itself needs no install step on COS either — it ships baked into the base image, which is the point of choosing COS for this host in the first place. Plain `docker run` was already how this host's containers were actually started (see `scripts/setup-cicd.sh` and `scripts/watchtower-webhook-setup.sh`); this ticket's script formalizes that into one idempotent, non-interactive, re-runnable form rather than introducing a tool (compose) that doesn't actually work here.

We considered and rejected baking a custom disk image (Packer or similar) — this is a single, rarely-rebuilt Always Free VM; the cross-compile/upload/versioning overhead of image baking doesn't pay for itself at this scale. Revisit only if the host starts getting rebuilt often enough for that to matter.

We also rejected automating deployment of *host* config changes (e.g. CI pushing to the host on every merge) — unlike the app's own Docker image, which already has a fully automated push-to-`stable`-then-Watchtower-redeploys path (ADR-0008), a host config change (a new Caddy route, a changed volume) is rare and worth a deliberate manual step, not another thing to keep secure and working unattended. The sync model is manual: edit `deploy/Caddyfile` or `scripts/provision-host.sh` in a PR same as any other change, then re-run `scripts/provision-host.sh` against the host by hand (it's idempotent — safe to re-run any time).

One gotcha worth stating plainly, since it's caused a real incident (a Caddy route misconfiguration during #63): all three containers reach each other by **container name** over the shared `eve-trader-net` user-defined bridge network, via Docker's embedded DNS — never via `localhost` or a published host port. Each container's own `localhost` is its own isolated network namespace; `watchtower:8080` works from Caddy, `localhost:8080` does not.

**Adopting this on the currently-running host is a one-time cutover, not a transparent re-run.** `scripts/provision-host.sh`'s `docker run` invocations were verified, command by command, against the real host's actual `docker inspect` output (images, mounts, network, ports, restart policy, cmd) — they match. But the script's `~/eve-trader-deploy/` layout is a fresh location, not the host's current one: the live Caddy data lives under `/home/Michael.Goodness/eve-trader/...` (note the capitalized username — a pre-existing quirk on this host, a separate directory from the `michael.goodness` account the script's `gcp_ssh` actually connects as, which can't even read into it; `cat`ing the live Caddyfile via that account returns Permission denied). Running the script as-is would therefore start Caddy against an *empty* `caddy-data`, and Caddy would re-request fresh Let's Encrypt certificates rather than reuse the existing cache — a real, if temporary (a few minutes, not indefinite, assuming no rate limit is hit), TLS gap, not a no-op. A real cutover should first `docker cp`/copy the existing `caddy-data`/`caddy-config` contents into `~/eve-trader-deploy/data/` (as the account that can read them) before running the script, or accept the brief cert-reissue gap. Recreating `eve-trader` and `watchtower` themselves is a few seconds of downtime each either way, with no data loss (their bind-mounted directories aren't affected by this quirk). This is why this ticket's live verification stopped short of actually invoking the script against production — that's a deliberate cutover to schedule with the certificate consideration above in mind, not something to run unattended as part of writing this script.
